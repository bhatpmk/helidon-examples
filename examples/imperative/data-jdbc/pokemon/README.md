# Helidon Data JDBC imperative Pokémon example

This example exercises the same read, paging, update, generated-key, and local-transaction features as the declarative Pokémon example. It uses the public `JdbcClient` API directly; there is no repository interface or annotation processor.

The named `JdbcClient` is supplied by the JDBC provider from `data.sources` and `data.persistence-units.jdbc` in `src/main/resources/application.yaml`. The persistence unit runs `init.sql` when the application starts. The example uses MySQL and HikariCP.

## Build and run

Start a MySQL database that matches the configuration, then run:

```shell
mvn package
java -jar target/helidon-examples-imperative-data-jdbc-pokemon.jar
```

The application is available below `http://localhost:8080/pokemon`.

## Operations

| Request | Imperative operation |
| --- | --- |
| `GET /pokemon/all` | `create(SQL).options(options).map(ROW_MAPPER).list()` |
| `GET /pokemon/type/Normal` | Positional `bind(1, "Normal", JDBCType.VARCHAR)` followed by `list()` |
| `GET /pokemon/page/0/5` | Explicit `LIMIT ? OFFSET ?` SQL followed by `list()` and a count query |
| `GET /pokemon/after/5/5` | Explicit key-set paging SQL followed by `list()` |
| `GET /pokemon/types` | Scalar record mapping with `map(TYPE_MAPPER).list()` |
| `GET /pokemon/get/Meowth` | `map(ROW_MAPPER).optional()` |
| `POST /pokemon` | `generatedKeys(...).one()` followed by a transaction-bound read |
| `DELETE /pokemon/20` | `execute()` returning the update count |

The insert method uses `@Tx.Required`. The provider binds all calls in that method to one local JDBC transaction and owns the connection lifecycle. The imperative code uses positional JDBC parameters (`?`); named parameter rewriting is a declarative code-generation feature.

The generated-key mapper reads the `ID` column by index. The typed `VARCHAR` bind in the type query shows the imperative equivalent of a declarative `@Data.JdbcType` override.

Dynamic sorting and paging are not generated by the provider. This sample keeps both operations in explicit SQL so the application can choose syntax supported by its database driver.
